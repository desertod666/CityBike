# BafangReader / CityBike

Пассивный CAN-ридер на **ESP32-C3 Super Mini**: открытая Wi-Fi-точка с локальной панелью и переносная Windows-программа для записи USB-потока на диск.

**При включении CAN остановлен. Только listen-only.** Передачи CAN, replay, изменения параметров и прошивки контроллера Bafang нет. Скорость велосипедной шины и совместимость приложенного словаря с конкретным контроллером пока не подтверждены.

## Скачать и запустить

- [Windows x64 — последняя программа](https://github.com/desertod666/CityBike/releases/latest/download/BafangReader-Windows-x64.zip)
- [Выпуски и прошивки ESP32-C3](https://github.com/desertod666/CityBike/releases/latest)

Распакуйте ZIP и запустите **BafangReader.exe**. Откроется панель в обычном браузере на `127.0.0.1` с автоматически выбранным локальным портом. Выберите COM-порт ESP32 и нажмите «Подключить». По умолчанию выбран режим «По отметке»: выберите скорость вручную или нажмите «Найти скорость CAN», выберите 30/60 секунд, опишите действие и нажмите «Добавить отметку». Эта кнопка запускает listen-only CAN и запись всех прочитанных байтов. По таймеру или кнопке «Остановить» CAN останавливается, файлы закрываются. Новая отметка во время записи начинает отсчёт заново. В режиме «Непрерывно» запись запускает «Начать приём». До запуска запись на диск не создаётся; экранные фильтры не влияют на записываемые кадры.

Python и интернет для записи не требуются. Интернет нужен для обновлений и необязательной отправки завершённых записей на настроенный сервер.

## Встроенная Wi-Fi-панель

После подачи USB-питания появляется открытая сеть **BafangReader-XXXX**, где XXXX — окончание MAC точки доступа. Пароля нет. Адрес: **http://192.168.4.1**. Имя и адрес также входят в USB STATUS.

Есть DNS/HTTP captive portal: ОС может предложить открыть страницу после подключения к сети. Автоматическое открытие зависит от ОС; адрес `192.168.4.1` остаётся основным способом входа.

Панель содержит живое состояние, выбор скорости, START/STOP, статистику потерь, сырые кадры, отметки действий, тест/полярность LED и настройки имени/канала Wi-Fi. Настройки сохраняются только при остановленном CAN; имя и канал сети применяются после перезапуска питания. Wi-Fi всегда открытый. Сеть не предоставляет интернет; подключённые к ней клиенты могут управлять пассивным приёмом.

**Веб-просмотр ограничен:** кольцо ESP32 на 256 кадров, выдача до 64 кадров за запрос, в браузере последние 500 показанных кадров. Пропуски просмотра отображаются отдельно. «Снимок просмотра» экспортирует только этот буфер и отметки, а не полный CAN-архив. Для длительной записи используйте Windows-программу по USB. На ESP32 постоянное хранение логов пока не реализовано.

## Подключение аппаратуры

| ESP32-C3 | SN65HVD230 / VP230, 3,3 В |
|---|---|
| 3V3 | VCC / 3V3 |
| GND | GND |
| GPIO4 | CTX / TXD |
| GPIO5 | CRX / RXD |

ESP32 питается только от USB, трансивер — от её 3V3. Аккумуляторное напряжение не подключается. GPIO8 — штатный LED/strapping pin, внешняя нагрузка не добавляется. Полярность LED проверяется визуально командами LOW/HIGH, затем выбирается в настройках.

CANH, CANL и сигнальная земля подключаются к велосипеду только после подтверждения распиновки и напряжений. Модуль не имеет гальванической развязки. Дополнительный терминатор 120 Ом на модуле не нужен при подключении к уже согласованной шине с двумя штатными терминаторами; это проверяется по конкретной системе.

## Что записывает Windows-программа

Файлы находятся в `%LOCALAPPDATA%\BafangReader\logs\<сеанс>`. Точный путь показан в панели.

| Файл | Содержание |
|---|---|
| `wire.bin` | Все USB-байты, которые прочитала программа, до разбора |
| `capture.jsonl` | Исходные строки, кадры, расшифровки, команды, отметки, смены сеансов и пропуски |
| `frames.csv` | Все принятые во время записи кадры, включая неизвестные ID, RTR и неверную длину |
| `completed.json` | Причина завершения, число кадров, версия программы и последнее состояние устройства |

Каждый кадр содержит полный ID, extended/RTR, DLC, DATA, sequence, boot/epoch, время ESP и время ПК. `t_us` — программное время чтения кадра из очереди TWAI, микросекунды с загрузки, а не аппаратная метка на CAN-проводе. RTR сохраняется с исходным DLC и пустыми DATA.

При переподключении новый сеанс начинается с остановленного CAN. GUI требует явного повторного подключения; консольный сборщик также поддерживает `--reconnect` с проверкой прежней USB-идентичности и без повторного автоматического START.

Сохранение каждого прочитанного байта не гарантирует отсутствие потерь до ПК: ограничены пропускная способность USB, очереди ESP32 и скорость диска. Счётчики потерь и sequence сохраняются. Максимальная нагрузка реальной шины ещё требует стендовой проверки.

## Обновления программы и ESP32

Для обновлений отдельный сервер не нужен. GitHub Releases хранит ZIP программы, ZIP прошивки и `latest.json` с версией, размерами и SHA-256. Постоянные ссылки ведут на последний выпуск. Проверка обновлений идёт в фоне; отсутствие интернета не блокирует USB-диагностику.

- «Обновить программу»: скачивание, проверка хеша, остановка CAN/закрытие логов, запуск новой версии из пользовательской папки обновлений.
- «Обновить ESP32 по USB»: скачивание, проверка архива и каждого образа/смещения, остановка CAN, проверка USB-идентичности и чипа C3, запись через esptool, повторное подключение и проверка новой версии через STATUS.

Перед обновлением ESP32 отсоедините CANH/CANL от велосипеда и сохраняйте USB-питание до завершения записи. Обновление ESP32 через открытую Wi-Fi-сеть не предоставляется. Прошивка рассчитана на C3 с flash 4MB и factory-разделом 2MB; на ESP32-S3 не записывать.

SHA-256 проверяет целостность загрузки; доверие к издателю обеспечивается HTTPS и выбранным репозиторием. Это не цифровая подпись исполняемого файла.

## Сборка из исходников на Windows

ESP-IDF 5.5.0, PlatformIO Core 6.2.0, espressif32 6.12.0, Python 3.11, pyserial 3.5. Для упаковки EXE: PyInstaller 6.22.3 и esptool 4.9.0.

```bat
build.bat
flash.bat COM9
launch_pc.bat
collect.bat --port COM9
```

`build.bat` и `flash.bat` используют Python установленного расширения PlatformIO. ESP-IDF/PlatformIO не поддерживают пробелы в пути сборки: скрипт копирует только исходники и конфигурацию в отдельный кэш `%USERPROFILE%\.platformio\reader-builds\bafang-<hash>`, затем возвращает бинарники и фактический sdkconfig в `artifacts/`. Текущая рабочая папка остаётся главным экземпляром исходников.

`launch_pc.bat` запускает браузерную USB-панель из Python. `collect.bat` — прежний консольный сборщик; команды: `help`, `status`, `start 125000`, `stop`, `mark действие`, `led low`, `led high`, `led auto`, `quit`. Число 125000 здесь пример команды, не установленная скорость велосипеда.

`setup_pc.bat` устанавливает pyserial в отдельную .venv. `build_pc.bat` создаёт среду упаковки и собирает проверенные release-архивы; перед ним должна пройти сборка ESP32. В VS Code задача сборки по умолчанию вызывает path-safe BAT.

```bat
test_pc.bat
node scripts\test_web.cjs
```

Все тестовые CAN-примеры искусственные. В публичной поставке есть только сокращённый словарь пяти ID: 02F83201, 04F83401, 01F83100, 04F83400, 03106300. Он был сверен с предоставленным оригиналом, но совместимость с конкретным велосипедом остаётся неподтверждённой. Исходный SYM, полные пользовательские таблицы, журналы устройства и резервные flash-образы не публикуются. При наличии исходных файлов локально декодер проверяет весь JSON/CSV против оригинала перед использованием.

## USB-протокол 1

ASCII-команда в строке LF/CRLF, до 79 символов, регистр USB-команд не важен. Нативный USB Serial/JTAG, параметр COM API 115200 не задаёт скорость CAN.

`HELP`, `STATUS`, `START <bitrate>`, `STOP`, `LED LOW|HIGH|AUTO`, `LED ACTIVE LOW|HIGH`, `WIFI <channel> <ssid>`.

Скорости, бит/с: 10000, 20000, 50000, 100000, 125000, 250000, 500000, 800000, 1000000. Windows-программа умеет искать скорость последовательными START/STATUS/STOP в listen-only. USB-команды и встроенная Wi-Fi-панель сохраняют ручной выбор. `WIFI` сохраняет открытый SSID длиной 1–32 ASCII-символа (латиница/цифры/пробел/дефис/подчёркивание) и канал 1–11; применяется при перезапуске. Сохранение Wi-Fi и полярности LED отклоняется при работающем CAN.

Ответы JSONL: hello/status/help/error/frame/log. Счётчики STATUS: received, frame_queue_drops, usb_frame_drops, rx_missed, rx_overrun, bus_errors, control_drops, command_drops, stop_discards, rec/tec, twai_state, запас стеков и heap. Суммы потерь не включают незаметные аппаратуре потери. Разрывы sequence и счётчики очередей могут описывать одни и те же потери; не суммируйте их повторно.

## Выпуск следующей версии

Обновите версию в `project.json`, `pc/updates.py`, `src/main.c` и `CMakeLists.txt`. Упаковщик проверяет их совпадение. После тестов и аппаратной проверки соберите архивы и опубликуйте новый `vX.Y.Z` с тремя assets из `release/`. Можно запустить workflow **Build release** вручную: без publish он выдаёт артефакты, с publish создаёт GitHub Release. Логи и исходный пользовательский SYM для сборки не нужны.

Служебные ESP-IDF-логи идут типом `log` через отдельную ограниченную очередь и общий USB writer. STATUS содержит sdk_log_drops/sdk_log_truncated. Для старых прошивок сборщик может восстановить целый JSON-ответ после обрывка служебного префикса; исходная строка и событие transport_resync сохраняются.

Закрытие последней вкладки Windows-панели автоматически останавливает CAN и завершает программу примерно через 8 секунд. Перезагрузка страницы успевает открыть новый сеанс. После аварийного завершения браузера действует резервный таймаут 120 секунд без heartbeat; фоновые вкладки не следует принудительно замораживать во время длительной записи. Во время прошивки ESP32 автоматическое завершение отложено до окончания операции. Кнопка завершения остаётся доступной для немедленного выхода.

## Автопоиск скорости CAN (Windows)

По кнопке программа проверяет девять скоростей по 1,5 секунды. Кандидат требует не менее пяти корректно принятых кадров и отсутствия новых bus_errors/rx_missed/rx_overrun за окно. Единственный кандидат выбирается в списке; после поиска CAN всегда останавливается. Ноль кадров не подтверждает скорость: возможны тихая шина, неверные провода или подключение. Несколько кандидатов не дают автоматического выбора. Успех на реальном велосипеде ещё не проверен; стенд без шины корректно даёт отсутствие результата. Во время поиска запись не ведётся; кадры каждого запущенного пользователем фрагмента сохраняются полностью.

## Автоматическая отправка записей (Windows)

Галочка «Отправлять записанные фрагменты на сервер» запоминается на этом Windows-пользователе, по умолчанию выключена. Включение не отправляет старые папки автоматически. Завершённые при включённой галочке записи попадают в постоянную очередь. Выключение прерывает текущую отправку и запрещает новые запросы; уже полученные сервером части отозвать нельзя. Очередь сохраняется для возобновления после включения. При закрытии программы незавершённая загрузка продолжится при следующем запуске. Самостоятельной постоянно работающей службы на ПК нет.

Отправляется tar.gz из wire.bin/capture.jsonl/frames.csv/completed.json, частями до 2 МиБ, по HTTPS с проверкой SHA-256 и подтверждением сервера. Ни локальные логи, ни неизвестные кадры не удаляются. Фильтры экрана и декодер не ограничивают состав архива. Доступ выдаётся отдельно каждому ПК; общего ключа сервера/GitHub/Cloudflare в EXE нет. Кэш учётных данных защищён Windows DPAPI. Без настроенного адреса и ключа очередь остаётся на ПК.

Серверный код находится в `server/`: закрытый приёмник на localhost:18841 за HTTPS, данные `/opt/citybike/data`, отдельный пользователь и systemd-сервис. Общий резерв под архивы 2 ГиБ, минимум свободного места на диске 4 ГиБ; при достижении ограничения новая запись не принимается, локальный оригинал сохраняется. Автоматического удаления архивов нет. Публичных маршрутов чтения/списка логов нет; администратор разбирает их через SSH. Публикация ПО на GitHub не публикует пользовательские логи. Для постоянной интернет-работы требуется отдельно настроенный HTTPS-адрес; случайный тестовый trycloudflare-адрес не подходит как постоянная конфигурация.

Оценка на двух синтетических наборах по 10000 кадров: около 1,23 КБ/кадр на локальном диске и 52–96 байт/кадр после gzip (зависит от данных). При 100 кадрах/с минута отправки примерно 0,3–0,6 МБ, при 1000 — 3–6 МБ; локально до сжатия примерно 7,4/74 МБ соответственно. Это оценка формата, не измеренная скорость велосипеда и не обещание максимальной пропускной способности. Для первичного анализа рекомендуются короткие фрагменты с понятными отметками и повторением действий.
